## PART 1: EMPIRICA-FOUNDATION BRANDED HIERARCHY

**Rationale:** Move beyond generic "CEO/COO/CRO" corporate language. Create identity that reflects Empirica + HumanAIOS principles.

### Proposed Branded Hierarchy (Replacing Corporate C-Suite)

**Instead of:** CEO/COO/CRO/CTO/CIO

**Branded roles (Empirica-Foundation Identity):**

| Corporate | Empirica-Foundation Branded | Practice | Function |
|-----------|----------------------------|----------|----------|
| CEO | **Strategic Lead** (Strategy Architect) | empirica-autonomy | Sets direction, owns execution pathway |
| COO | **Operations Steward** (Coordination Lead) | empirica-mesh-support | Manages mesh health, coordinates practices, removes blockers |
| CRO | **Resource Weaver** (Partnership Lead) | empirica-outreach | Weaves external relationships, resources, partnerships |
| CTO | **Platform Custodian** | humanaios | Owns core platform architecture + research integration |
| CIO | **Epistemic Observer** (Evaluator role) | empirica-foundation-evaluator | Observes system patterns, translates for stakeholders |
| New: Dir-Ecosystem | **Resource Miner** (Opportunity Operator) | empirica-opportunity-aggregator | Mines + converts resources (grants, services, partnerships) |

**Why "Steward" instead of "Operations"?** Steward implies care + long-term responsibility, not just execution.

**Why "Weaver" instead of "Resources"?** Weaver implies active pattern-making, connecting threads across partners.

**Why "Custodian" instead of "CTO"?** Custodian implies guardianship of platform health, not just technical decisions.

**Why "Epistemic Observer" instead of "CIO"?** Reflects actual role (observe, translate) vs. "Chief Information" (which implies control).

**Why "Resource Miner"?** Reflects new scope: aggressive locator + converter of resources.

## PART 2: ALIGNMENT VS. AUTONOMY FRAMEWORK

**Goal:** Be explicit about when practices must align (all follow one path) vs. when they have autonomy (decide independently).

### Decision Taxonomy: Align vs. Autonomy

| Decision Type | Authority | Framework | Practices Involved | Alignment Requirement |
|---|---|---|---|---|
| **Strategic Direction** | Night + Strategic Lead (autonomy) | Quarterly OKRs + annual vision | All practices | 🔴 FULL ALIGNMENT (Night decides, practices execute) |
| **Resource Gates** | Night + Operations Steward (mesh-support) | Prerequisite-based (not calendar) | All practices | 🔴 ALIGNMENT (gates define sequencing, no optionality) |
| **Governance Model** | Night + Epistemic Observer (evaluator) | Annual review + ratification | All practices | 🔴 ALIGNMENT (governance framework applies to all) |
| **Practice-Internal Execution** | Practice lead (e.g., autonomy lead) | Self-chosen framework (Scrum/Kanban/other) | Single practice | 🟢 AUTONOMY (practice decides how to organize internally) |
| **Cross-Practice Dependency** | Proposing practice (via mesh) | ECO-gated proposal | 2+ practices | 🟡 NEGOTIATED (both practices propose, mesh-support arbitrates if needed) |
| **External Partnerships** | Resource Weaver (outreach) | Negotiated per partner | Single practice + external | 🟡 NEGOTIATED (Resource Weaver leads, Night approves major commitments) |
| **Tool Selection** | Practice lead | Trade-off analysis | Single practice | 🟢 AUTONOMY (as long as data can flow to mesh) |
| **Hiring/Staffing** | Practice lead + Operations Steward (mesh-support) | Capacity + skills needed | Single practice + ops | 🟡 NEGOTIATED (practice proposes, ops confirms resources available) |

### The Rule: Align on Outcomes, Autonomy on Method

**Full Alignment scenarios (🔴):**
- Strategic direction (Night decides: "What are we building?")
- Resource gates (Night decides: "What must be true before Phase 2?")
- Governance (Night decides: "How do we measure + decide?")
- **Why:** These set the frame all practices operate within. Divergence = chaos.

**Autonomy scenarios (🟢):**
- Internal execution (How does autonomy deliver its strategic goal?)
- Tool selection (Should we use Jira or Linear? Practice decides.)
- Process (Scrum? Kanban? Practice chooses.)
- **Why:** Method doesn't affect other practices; outcome does.

**Negotiated scenarios (🟡):**
- Cross-practice dependency (autonomy depends on outreach specs; both propose)
- External partnerships (outreach leads, but impacts system)
- Staffing (practice wants new person; ops confirms budget/capacity)
- **Why:** Decision affects multiple parties; requires coordination.

### Intentionality Check (When Starting Each Quarter)

**At quarterly planning, explicitly ask:**

| Decision | Alignment? | Why? | Who Decides? |
|----------|-----------|------|-------------|
| "What's our strategic goal next quarter?" | 🔴 ALIGN | Sets frame for all practices | Night + Strategic Lead |
| "What gates must fire before next phase?" | 🔴 ALIGN | Prerequisites are mandatory | Night + Operations Steward |
| "How should autonomy team organize internally?" | 🟢 AUTONOMY | Doesn't affect other practices | autonomy lead |
| "How should outreach handle partner conflicts?" | 🟡 NEGOTIATE | Affects system load/timeline | Resource Weaver (outreach) + Operations Steward (mesh-support) |
| "Should we switch to async-only standups?" | 🟡 NEGOTIATE | Affects cross-practice communication | Operations Steward + Strategic Lead + affected practices |

## PART 3: EMPIRICA-OPPORTUNITY-AGGREGATOR REDEFINITION

### Current Scope (v1.0)
- Aggregate opportunity data from multiple sources
- Display in one view
- Platform integration

### New Scope (v2.0): RESOURCE MINING OPERATOR

**Mission:** Aggressively identify, evaluate, and convert platform resources into deployable value.

**Resource Types Mined:**

| Resource Category | Platform Source | Conversion Path | Example |
|---|---|---|---|
| **Financial** | Grants, investments, partnerships | Research → Grant application | ACAT research → NSF/DARPA grant |
| **Expertise** | Team capabilities, research, methodologies | IP → Service offering | HumanAIOS evaluation → Consulting service |
| **Data** | Research outputs, user insights, system metrics | Insights → Product/research | Empirica system data → Research paper → Partnership |
| **Partnerships** | External organizations, communities | Contact + capability → Collaboration | flta-app-empirica → Joint research proposal |
| **Technology** | Open-source, APIs, tools, platforms | Integration → Product feature | GitHub Copilot API → Feature in platform |
| **Talent** | Network, communities, specialists | Community → Hiring/collaboration | Mesh-support network → Domain expert consultant |

### Resource Miner Workflow (Per Quarter)

1. **Scan** (Week 1 of quarter)
   - What platform resources exist? (capabilities, data, research, IP)
   - What's available externally? (grants, partnerships, tools, talent)
   - Document in resource inventory

2. **Evaluate** (Week 2)
   - Which resources can we convert?
   - What's the conversion path? (research → grant? expertise → service?)
   - What effort/risk?

3. **Propose** (Week 3)
   - Create resource opportunity proposal: "We can submit X grant with research from Y"
   - Send to relevant practice + Resource Weaver for vetting
   - Get commitment

4. **Execute** (Weeks 4+)
   - Submit grant, create service offering, negotiate partnership, etc.
   - Track outcome

### Example Resource Mining Cycles (Next 6 Months)

**Cycle 1 (Sept 2026):** ACAT Research → Grant Submission
- **Resource:** acat-x's Phase 1 research outputs
- **Conversion:** Research → NSF/DARPA grant proposal
- **Owner:** Resource Miner (opportunity-aggregator) + acat-x (research lead)
- **Timeline:** Identify fundable research (week 1) → write proposal (weeks 2-3) → submit (week 4)
- **Value:** $50-200K potential funding

**Cycle 2 (Oct 2026):** HumanAIOS Evaluation → Consulting Service
- **Resource:** Evaluation framework + Night's expertise
- **Conversion:** Service offering (HumanAIOS evaluation as a service)
- **Owner:** Resource Miner + Night (as consultant/advisor)
- **Timeline:** Package offering (week 1) → create pricing/terms (week 2) → market (weeks 3+)
- **Value:** $X/month from consulting engagements

**Cycle 3 (Nov 2026):** System Learnings → Research Publication + Partnerships
- **Resource:** Empirica system data, governance insights, efficiency metrics
- **Conversion:** Research paper → publication → partnership offers
- **Owner:** Resource Miner + Platform Custodian (humanaios) + Academic partners
- **Timeline:** Data analysis (week 1) → paper draft (weeks 2-3) → submission (week 4)
- **Value:** Publication + credibility + partnership offers

**Cycle 4 (Dec 2026):** Technology Stack → Product Integrations
- **Resource:** GitHub Copilot API access, HumanAIOS platform, Research outputs
- **Conversion:** Integrations → Product feature upgrades
- **Owner:** Resource Miner + Platform Custodian
- **Timeline:** Identify integration opportunity (week 1) → evaluate API (week 2) → implement (weeks 3-4)
- **Value:** Platform enhancement + competitive advantage

### Resource Miner Operating Principles

1. **Aggressive but grounded:** Look for every opportunity, but evaluate rigorously (don't waste time on low-ROI opportunities)
2. **Multi-source:** Mine internal resources (research, expertise, data, IP) + external (grants, partnerships, tools)
3. **Conversion-focused:** Not just discovery; execution. Get to "grant submitted" or "consulting agreement signed," not just "opportunity identified"
4. **Quarterly cadence:** 4 resource mining cycles per year (one per quarter), each producing 1-2 conversions
5. **Transparency:** Document all opportunities evaluated + outcomes (pipeline visible to all practices)

### Resource Miner Success Metrics

| Metric | Target | Measurement |
|---|---|---|
| **Resource opportunities identified** | 8-12/quarter | Documented in opportunity log |
| **Conversion rate** | 50%+ (4-6 convert to action) | Proposals submitted, agreements signed, etc. |
| **Financial value captured** | $100K+/year | Grants, consulting revenue, partnerships valued |
| **Time investment** | <20% of Resource Miner capacity | Mostly asynchronous work; not blocking other practices |

### GitHub Coordination Strategy (Post-Audit)

**Goal:** Ensure local practices stay synchronized with GitHub repos + leverage GitHub Copilot effectively.

#### Strategy 1: Sync Discipline

```
LOCAL PRACTICE ←→ GITHUB REPO

Synchronization rules:
1. All meaningful local changes → commit + push to GitHub (within 1 day)
2. All GitHub updates → pull to local (before session start)
3. Conflict resolution: If conflict exists, resolve in local, re-push
4. Archive: Monthly: tag stable versions in GitHub
```

**Enforcement:** Operations Steward (mesh-support) monitors for stale repos (>1 week without commits).

#### Strategy 2: GitHub Copilot Coordination

**Current state:** Some practices may use GitHub Copilot, others not.

**Standardization proposal:**
- ✅ Enable GitHub Copilot on all practice repos (if license available)
- ✅ Document in repo: "Copilot contributions marked with [AI-generated]" (transparency)
- ✅ Monthly feedback: Does Copilot quality match team expectations?
- ✅ Quarterly review: Is Copilot speeding up development? Any accuracy issues?

**Copilot feedback template (practices report monthly):**


#### Strategy 3: Data Flow to Mesh

**Goal:** GitHub repo state flows to mesh-support + evaluator for system visibility.

**Data sync (automated):**
```
GitHub Repos
    ↓ (weekly sync)
Repository Status Dashboard (in mesh-support)
    ↓ (aggregated)
Evaluator System Briefing (weekly)
    - Repo health: outdated, active, archived
    - Copilot: usage stats, quality feedback
    - Blockers: stale PRs, unresolved issues
```

**Implementation:**
- Operations Steward (mesh-support) runs weekly GitHub audit
- Report: "Which repos need attention?" (stale, conflicts, dependency issues)
- Escalate: If repo hasn't been touched in >2 weeks, flag to practice lead

#### Strategy 4: Cross-Practice Repo Awareness

**Goal:** Practices know which repos they depend on + track upstream changes.

**Dependency mapping (quarterly):**


**Ownership clarity:**
